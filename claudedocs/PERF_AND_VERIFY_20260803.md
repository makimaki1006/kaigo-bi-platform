## 何が遅かったのか

### ① 先頭ワイルドカードの LIKE には索引が効かない

施設名検索は `"事業所名" LIKE '%q%' OR "法人名" LIKE ... OR "電話番号" LIKE ...`。
223,103 行を舐め、しかも `search_facilities` は COUNT と本体で **2 回**実行していた。

内訳の実測: COUNT 22.2s / SELECT+LIMIT 29.3s。

**対処**: FTS5 の **trigram トークナイザ**（日本語の部分一致に対応）で
`facilities_fts` を構築し、MATCH のサブクエリで絞る。
索引が無い環境でも動くよう LIKE へフォールバックする（判定はプロセス内で1度だけ）。

### ② 法人単位の集約を毎回やっていた

M&Aスクリーニングは `GROUP BY "法人番号"` で 190,003 グループを作り、
`ORDER BY facility_count DESC` のため LIMIT が効かない。
段階的に計測すると GROUP BY + CAST 付き SUM だけで **115.5 秒**。

**対処**: `corp_summary`（68,563 法人・1法人1行）を事前構築。
施設数・従業者数・離職率・展開地域・サービス種別・財務フラグ・違反フラグを保持し索引を張る。
`ma_screening` / `dd_search` / `corp_group_top_corps` / ヒートマップの上位法人選定が
すべてこれを引く。未構築時は従来の集約にフォールバックする。

### ③ 集計対象の列を含まない索引は使われない

`GROUP BY prefecture` に `idx_fac_pref` はあったが、
`AVG(turnover_rate)` のため結局テーブル本体を読む必要があり 33.5 秒。

**対処**: `(prefecture, turnover_rate)` の複合索引で **0.2 秒**。
同様の索引を `scripts/build_indexes.py` にまとめた。

### ④ TEXT 列の CAST が索引を殺す

`従業者_合計` `定員` `quality_score` `kasan_count` は TEXT 型。
ベンチマークのパーセンタイルは 8 指標 × 3 スコープで比較するが、
CAST を挟むため索引が効かず、指標ごとにクエリを分けても 47 秒だった。

**対処**: `facility_metrics`（223,103 行）に REAL へ変換した列を持たせ、
指標別・スコープ別の索引を張る。

### ⑤ Turso はリモート実行なので往復回数が効く

1 クエリあたり約 2 秒のオーバーヘッドがある。
指標ごとに 24 クエリへ分割したら逆に遅くなったため、
スコープ単位の 1 クエリ（計 3 回）へまとめ直した。

## 表示が壊れていた実バグ

| 症状 | 原因 |
|---|---|
| 加算ヒートマップが「データなし」 | API は `{ corps }` だけを返していたが、`HeatmapChart` は行ラベル・列ラベル・値の2次元配列を取る。`facilities` / `values` / `kasan_items` を返すよう修正（法人あたり4行に制限） |
| 「最大施設数法人」が常に「-」 | ETL は `max_facilities`、画面は `max_facilities_count` を参照。キー名の不一致。ETL を新キーに揃え、画面側にもフォールバックを追加 |
| 加算ヒートマップのキャッシュ | `kpi_cache` に旧スキーマ（`kasan_N_rate` の配列）が入っており、新形式でない場合は使わないようガード |
| M&Aの「魅力度スコア算出基準」 | 既に存在しない4カテゴリ加重平均の説明が残っていた。実際の固定しきい値の表に差し替え |

## 賃金データの数値化を修正

既定表示（キャッシュ）とフィルタ適用時（Rust）で**数字が食い違っていた**。

| 問題 | 内容 |
|---|---|
| 対象列 | Rust は `賃金_月額1` のみ、ETL は 1〜5 を unpivot。Rust も5列に揃えた |
| 表記ゆれ | 生値 12,835 件のうち素の CAST で拾えたのは 5,870 件。`250,000` → 250、`25万円` → 25 と誤変換されていた |
| 対処後 | カンマ・全角数字・「万」表記を両側で正規化。**11,350 件（SQL）/ 11,016 件（ETL）** に増加。平均 243,115 円 vs 242,364 円 |
| 残差 | 334 件。CAST が `30000～50000` のような値を許容し Python の `float()` は弾くため。実用上は無視できる差と判断 |

レンジも ETL に合わせて 10,000〜2,000,000 円に統一した。

### 定員の異常値
`facility_metrics` 構築時に判明。定員欄に **20251215（日付）** のような値が 97 件混入し、
全国平均定員が 557.5 名になっていた。1〜500 に制限して **43.5 名**（妥当）に是正。

## ETLが動かなくなっていた（修正済み）

`aggregate_to_cache.py` を実行しようとしたところ、**そもそも起動できない状態**だった。

```
requests.exceptions.InvalidSchema:
No connection adapters were found for 'libsql://...turso.io/v2/pipeline'
```

`turso_helpers.get_turso_config()` が環境変数の `libsql://` をそのまま返しており、
HTTP API を叩く `requests` が扱えなかった。`https://` へ変換する処理を追加した。

**これが kpi_cache が 2026-03-27 のまま更新されていなかった理由**。
つまり既定表示は4か月以上前の集計を出し続けていた。

再生成の前に `kpi_cache_backup_20260803` へ全行を退避してある。

## 未ジオコーディング分の補完（実施済み）

`scripts/geocode_fallback_gsi.py` を用意した。国土地理院API（無料・キー不要）で
残り 8.8% を解決する。ただし **そのまま使うと誤った座標が付く**ことが dry-run で分かった。

dry-run で判明した問題:

| 入力 | APIの返答 | 実際 |
|---|---|---|
| 北海道文京台東町11-24 | 札幌市中心部の座標 | **江別市**文京台東町 |
| 北海道南1条東2丁目8-2 | 富良野あたりの座標 | 市区町村が不明 |

国土地理院APIは曖昧な入力にも「それらしい」座標を返す。そこで次の検証を入れた。

- 入力に市区町村が無い住所は**採用しない**（どこにでも寄せられてしまうため）
- 入力と結果の市区町村が食い違えば採用しない
- ただし `阿寒郡鶴居村` と `鶴居村`、`端野町2区` と `端野町二区` は
  郡名・数字表記の違いなので同一とみなす
- 日本の緯度経度範囲外は捨てる

60件で試したところ**採用率 81.7%**。棄却されるのは市区町村や区が欠落した住所で、
どんな座標を付けても推測になるものだった。

```bash
python scripts/geocode_fallback_gsi.py --dry-run --limit 100  # 精度の確認
python scripts/geocode_fallback_gsi.py --limit 2000           # 分割実行も可
```

### 実行結果（2026-08-03・承認を得て実施）

| 項目 | 値 |
|---|---|
| 処理対象 | 18,196 件 |
| 採用 | **15,769 件（86.7%）** |
| 不採用 | 2,427 件 |
| 所要 | 約 2.5 時間 |

**座標付与率 91.2% → 99.0%（220,865 / 223,103）**

検証:
- 日本の範囲外 **0件**（緯度 24.333〜45.418 / 経度 122.988〜145.663）
- 都道府県ごとの座標中心が地理的に整合
  （北海道 43.1,141.9 / 東京 35.7,139.6 / 大阪 34.7,135.5 / 沖縄 26.1,127.5）
- ユニーク座標 58,186 → **65,030**（番地レベルの解決が効いて分散が増えた）
- 周辺検索の実測: 半径3km 77件 / 0.58秒、10km 830件 / 0.80秒

残る 2,238 件（1.0%）は都道府県すら空の 403 件を含み、
市区町村が特定できず「どこに置いても推測」になるもの。座標なしのまま残している。
