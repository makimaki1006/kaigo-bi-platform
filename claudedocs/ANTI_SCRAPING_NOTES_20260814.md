## 1. いま何があるか（調査結果）

| 仕組み | 実装場所 | 対象 |
|---|---|---|
| レート制限 | `kaigo-bi-backend/src/auth/rate_limit.rs` | **ログイン失敗・サインアップ・パスワードリセットのみ** |
| 監査ログ | `audit_logs` テーブル | ログイン/ログアウト/パスワード変更/ユーザー管理操作 |
| CSV出力ログ | `export_logs` テーブル | エクスポートの行数・ユーザー・日時 |
| 月間エクスポート上限 | `routes/export.rs` の `monthly_export_limit()` | プラン別のCSV出力行数 |
| プラン別ゲート | `routes/mod.rs` の `require_plan()` | 機能単位のアクセス可否 |

### 足りないもの

1. **通常APIの利用量が一切記録されていない。**
   `audit_logs` に入るのは認証・ユーザー管理だけ。
   施設検索・施設詳細・各種集計を何回叩いたかは残らない。
   → **今この瞬間に全件を舐められても、後から気づく手段がない。**

2. **通常APIにレート制限がない。**
   `rate_limit.rs` は認証系にしか適用されていない。
   `/api/facilities/search?per_page=500` を回されると
   223,103施設 ÷ 500 = 447リクエストで全件取得できる。

3. **レート制限がメモリ内。**
   `HashMap` + `Mutex` の単一インスタンス前提（コメントに明記あり）。
   Renderを再起動すればカウンタは消え、複数インスタンスにすると効かない。

4. **同時ログインの検知がない。**
   1アカウントを複数人・複数拠点で使い回しても分からない。

## 2. やるならこの順

コストの低い順。**①②だけでも「気づける」状態にはなる。**

### ① アクセスログを取る（検知の土台）

`api_access_logs` を作り、認証済みリクエストを1行ずつ残す。

```sql
CREATE TABLE api_access_logs (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  path TEXT NOT NULL,
  method TEXT NOT NULL,
  query TEXT,              -- per_page や filter を見たいので残す
  row_count INTEGER,       -- 返した件数 = 持って行かれた量
  status INTEGER,
  ip TEXT,
  user_agent TEXT,
  duration_ms INTEGER,
  created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX idx_aal_user_time ON api_access_logs (user_id, created_at);
```

実装は Axum のミドルウェアで、`auth_middleware` の後段に1枚挟む。
**書き込みが同期だとレスポンスが遅くなるので、`tokio::spawn` で投げっぱなしにする。**
Turso への書き込みが増えるため、バッファして数十件まとめて入れるのが望ましい。

### ② 取得量をアカウント単位で集計する

`row_count` を日次・アカウント別に集計し、管理画面に出す。

| 指標 | 意味 |
|---|---|
| 1日の取得行数 | 通常利用なら数千行。数万行が続けば異常 |
| 検索APIの呼び出し回数 | ページングを機械的に回していないか |
| 深いページ番号の割合 | `page=200` のような人が押さない操作 |
| 深夜帯の比率 | 人間の業務時間から外れた利用 |
| IP数 / User-Agent数 | 1アカウントの共有・自動化の兆候 |

既存の管理画面（`/admin`・操作ログ）に「利用状況」タブを足すのが自然。

### ③ 通常APIにレート制限をかける

認証系と同じ `rate_limit.rs` を流用できるが、**保存先をDBに移す必要がある**
（再起動で消える／複数インスタンスで効かない、という現在の制約のため）。

| 対象 | 案 |
|---|---|
| 検索API | 1分60回・1時間600回 |
| `per_page` | 現状500が上限。**100に下げる**だけでも全件取得のコストが5倍になる |
| 詳細API | 1分120回 |
| CSV出力 | 既に月間上限あり（維持） |

### ④ 抑止と追跡

| 手段 | 効果 | 副作用 |
|---|---|---|
| **透かし（ダミーレコード混入）** | 流出先を特定できる | データの正確性を毀損するので慎重に |
| CSVにアカウント識別子を埋める | 出所の特定 | ほぼ無害。**最初にやる価値がある** |
| 異常時のアラートメール | 気づける | 閾値調整が要る |
| 一時的な自動停止 | 被害を止める | 誤検知で正規利用者を止める危険 |

> 透かしは「気づく」ためには有効だが、BIの数字に嘘を混ぜることになる。
> **少なくとも集計値には入れない**こと。入れるならエクスポートの行単位に限る。

### 対策後（データAPIにレート制限を追加）

| 区分 | 対象 | 分あたり | 時間あたり |

`access_log` を `rate_limit` の**外側**に置いたので、429で弾いた分も記録される。
実測で 429 が 38件ログに入った。

### 検知の自動判定

`check_api_usage.py` に要注意アカウントの自動判定を追加。実測で攻撃アカウントを名指しできた:


判定条件（暫定・数日ログを溜めて調整する）:
リクエスト過多(>500/日) / 取得量過多(>20MB/日) / レート制限到達 / 検索連打(>100/日) / IP分散(>3)

### 正常利用が壊れないことの確認

**ここが一番大事。** 別アカウントでブラウザから施設マスタを開き、
「次へ」で3ページめくったが、**429は一度も出ず**（全リクエスト200）。
画面のページ送りは1操作あたり数リクエストで、上限20/分には遠く届かない。

### 残る限界（正直に）

- **画面を人が見て書き写す**のは止められない。目的は大量・自動の取得を割に合わなくすること。
- レート制限のカウンタは**メモリ内**。再起動で消え、複数インスタンスでは効かない。
  Renderを複数台にするなら共有ストア（Redis等）へ移す必要がある。
- 閾値は実測に基づく暫定値。正常利用の水準がログから見えたら調整する。

## 6. スクリーンショット収集への耐性（2026-08-16 実証）

「JSONで抜くのを塞いでも、画面を撮ってOCRすれば抜けるのでは」を検証した。
**結論: スクショ収集も同じAPIを叩いてページを描画するので、同じレート制限に当たる。**

### 実証（実際のブラウザから）

Playwrightで開いた実ブラウザの中から、収集ボットのデータ取得層を再現した:

| 撃ち方 | 結果 |
|---|---|
| ブラウザ内から詳細API 200連射 | 200が120件 / **429が80件**（上限120/分で頭打ち） |
| レート枠を使い切った状態で施設マスタを開く | バナー「アクセスが集中しています」+ **テーブルは「該当するデータがありません」** |

→ レート制限に当たった画面を撮っても、**写るデータはゼロ**。スクショ収集は成立しない。

### 単一ブラウザは自然に制限内に収まる（正規ユーザーは誤発火しない）

一覧API 25本をブラウザから並列で撃っても全部200だった。
ブラウザは1ホストあたり同時6接続に制限され、かつ一覧APIが1本25秒と重いため、
単一タブでは分あたり20本に自然と届かない。
**高速化するには並列クライアントが要り、そこで429に当たる。**

### 429時のUI

`isRateLimited` を追加し、施設マスタ等で専用バナーを出すようにした
（`components/common/ApiErrorBanner.tsx`）。正規ユーザーが偶発的に当たっても
「不正」ではなく「アクセスが集中／少し待って／CSVを使って」と案内する。

### スクショ収集は JSON より不利

画面描画 + OCR のオーバーヘッドがある分、JSON直叩きより遅い。
しかも取得の律速は同じ検索API（同じ上限）。**割に合わなさは JSON 経路以上。**
