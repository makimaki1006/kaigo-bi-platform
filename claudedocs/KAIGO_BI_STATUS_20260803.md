## 2. パフォーマンス

Playwright で実画面を検証したところ、**表示が壊れていたのではなく「遅すぎて表示に至っていない」**ページが多数あった。原因はすべて 223,103 行の全表スキャン。

| エンドポイント | 改善前 | 改善後 |
|---|---:|---:|
| `dd/search`（法人名検索） | 138.5s | 1.4s |
| `benchmark/{id}` | 73.4s | 2.2s |
| `facilities/search`（施設名検索） | 57.6s | 0.8s |
| `external/hiring-difficulty` | 47.6s | 1.1s |
| `facilities/nearby`（半径3km） | 40.6s | 0.5s |
| `ma/screening` | 数分（10分でも未完） | 0.8s |
| `corp-group/kasan-heatmap` | 数分 | 0.75s |

### 効いた原理（今後同種の問題に当たったとき用）

1. **先頭ワイルドカードの LIKE に索引は効かない** → FTS5 trigram
2. **GROUP BY の集約は事前計算できる** → `corp_summary`
3. **集計対象の列を含まない索引は使われない** → `(prefecture, turnover_rate)` で 33.5s→0.2s
4. **TEXT 列の CAST が索引を殺す** → `facility_metrics` で REAL 化
5. **Turso はリモート実行なので往復回数が効く**（1クエリ約2秒）→ クエリを分割しすぎない

## 3. 修正したバグ

### 参照名が実体と合っていない系（最多）

| 箇所 | 内容 |
|---|---|
| `cost-breakdown` | `monthly_amount` 列が無い（実際は `annual_amount_yen`）→ 500 |
| `revenue_kpi` | `処遇改善加算フラグ` 列が無い → フィルタ時に 500 |
| 加算ヒートマップ | `加算_特定I` が無い（実際は `加算_特定事業所I`）。エラーを握り潰して無言で空 |
| 賃金3クエリ | `salary_representative` 列が無い（実際は `賃金_月額1〜5`） |
| 採用天気図 | `job_offers_rate` が47県すべてNULL → 全県 1.00 |

再発防止として、バックエンド全SQLのカラム参照を実スキーマ（90テーブル・583カラム）と機械的に突合した。

### APIが返していないフィールドを画面が読んでいた系

`oldest_years` / `new_facilities_5yr` / `total_facilities` / `kasan_items` / `avg_age` / `avg_tenure` / `max_facilities_count`。
`types.ts` の全フィールドをバックエンド識別子2,031件と突合して検出した。

### 構造の食い違い

- 加算ヒートマップ: API は `{ corps }` だけ返すが `HeatmapChart` は行ラベル・列ラベル・値の2次元配列を取る
- `ma_screening` / 周辺検索: 事業所番号が33,100件重複（1事業所×1サービスで1行）していたため集約が必要だった

### ETL が起動できない状態だった

`turso_helpers.get_turso_config()` が `libsql://` をそのまま返し、`requests` が `InvalidSchema` で落ちていた。
**これが `kpi_cache` が 2026-03-27 のまま4か月以上更新されていなかった理由。**

## 5. ジオコーディング（Google を使わなかった理由）

**国土交通省「位置参照情報」**（無料・キー不要・商用可）で 91.2%、
**国土地理院API**（同）の補完で **99.0%** に到達。費用0円。

Google を採用しなかったのは3点。

1. **精度差がない** — 国土地理院APIは10/10成功、番地レベルまで一致
2. **コスト** — Google Geocoding なら22万件で概算 $1,100
3. **規約が現行構成と非互換** — 地図が Leaflet + OpenStreetMap。Google Maps Platform 規約は「Google Maps Content を Google マップ以外の地図上に表示すること」を禁じている

### Google口コミについて（調査結果）

蓄積して売るモデルは**成立しない**。

- Places API のレビューは **1施設あたり最大5件**しか返らない
- Google Maps Content は**キャッシュ・保存が原則禁止**（Place ID のみ例外）

規約内で成立する唯一の形は「施設詳細に Google Maps を埋め込み、口コミは Google のUI内で見せる。自社では保存も分析もしない」。

※ 料金・規約は改定される。最終判断前に公式規約を確認すること（上記は2026年5月時点の知識）。

### 補完時の注意（重要）

国土地理院APIは**曖昧な入力にも「それらしい」座標を返す**。
`北海道文京台東町11-24`（実際は江別市）が札幌中心部に解決された。
そのため `geocode_fallback_gsi.py` では次を検証している。

- 入力に市区町村が無い住所は**採用しない**
- 入力と結果の市区町村が食い違えば採用しない（郡名・漢数字の差は同一とみなす）
- 日本の緯度経度範囲外は捨てる

採用率86.7%。**残る1.0%（2,238件）は意図的に座標なしのまま**。

## 6. 実装した機能

### 周辺施設マップ `/facility-map`

選んだ施設を中心に、半径内の施設を地図と一覧で可視化する。

- `GET /api/facilities/nearby?center=<事業所番号>&radius_km=&<filters>`
- 矩形でSQL絞り込み → Haversine で厳密化 → 距離昇順
- 半径 1/3/5/10/20/30km、法人種別・サービス種別・従業者数下限で絞り込み
- 中心ピンをオレンジで強調、半径円、自動ズーム
- 周辺のサービス構成、距離順の一覧

### M&A絶対基準スコア

偏差値は母集団で変動するため不採用。**固定しきい値の加点のみ**。

| 指標 | しきい値 | M&A観点 | 営業観点 |
|---|---|---:|---:|
| 施設数 | 10+ / 3-9 / 1-2 | 30/20/10 | 40/25/10 |
| 従業者数 | 200+ / 50-199 / <50 | 25/15/5 | 25/15/5 |
| 展開都道府県数 | 3+ / 2 / 1 | — | 25/15/5 |
| 決算データあり | — | 15 | — |
| 債務超過・営業赤字なし | — | 20 | — |
| 行政処分・指導なし | — | 10 | 10 |

規模バッジ: 施設数10+ または 従業者200+ = 大 / 3+ または 50+ = 中 / それ以外 = 小

## 7. 運用手順

スクレイピングで施設データを更新したら、次を順に実行する。

```bash

python scripts/geocode_facilities.py --match --apply   # 緯度経度（位置参照情報）
python scripts/geocode_fallback_gsi.py                 # 残りを国土地理院APIで補完（要3時間）
python scripts/build_search_index.py --refresh         # 施設名の全文検索
python scripts/build_corp_summary.py --refresh         # 法人単位の集計
python scripts/build_facility_metrics.py --refresh     # ベンチマーク指標
python scripts/build_indexes.py --build                # 索引（冪等）
python scripts/aggregate_to_cache.py                   # kpi_cache（約27分）
```
