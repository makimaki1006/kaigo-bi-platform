### ③ Turso のオーバーヘッド（技術的に誤った結論）

**誤: 「1クエリ約2秒のオーバーヘッド」**

ベンチマークを指標ごと24クエリに分けたら47秒だった事実から逆算したが、
それは当時インデックスが効かず**各クエリ自体が重かった**ためで、往復コストではない。

実測:

```
SELECT 1 を10回        中央値 0.066s（最小 0.051s / 最大 0.135s）
索引の効く集計を5回      中央値 0.069s
SELECT 1 ×24 を1リクエストにまとめ  0.069s
SELECT 1 ×24 を24リクエストに分割   1.623s
```

**正: 1往復 約0.066秒。** 24分割すると1.62秒積み上がる（まとめた場合の23倍）。
「クエリを分割しすぎない」という結論自体は正しいが、根拠の数値が1桁以上違っていた。

`CLAUDE.md` / `KAIGO_BI_STATUS` / `PERF_AND_VERIFY` / `sql_aggregator.rs` の
4箇所すべてを訂正した。

### ⑤ 座標付与率 91.2%（定義の取り違え）

帳尻が合わないことから発覚。

```
補完前 203,499 + fallback採用 15,769 = 219,268
実測                                   220,865
差                                       1,597  ← 説明できない
```

調査結果:

| 値 | 意味 |
|---|---|
| 203,499 | 突合**CSVの行数** |
| 174,080 | そのユニーク事業所番号 |
| **205,056** | それが `facilities` で占める**行数**（= 91.9%） |

事業所番号は「1事業所 × 1サービス」で重複するため、**CSV 1行が複数行を更新する**。
`203,499 / 223,103 = 91.2%` は行数と件数を混同した計算だった。

**正: 91.9%（205,056行）→ 99.0%（220,865行）**

なお `205,056 + 15,769 = 220,825` で実測 220,865 とまだ40件差があるが、
これは fallback 側でも同じ事業所番号が複数行を更新した分。

「ユニーク座標 58,186 → 65,030」も母数が違う（203,499行時点 vs 220,865行）ため、
単純比較できない旨を併記した。

## この検証から得た教訓

1. **数字を書くときは定義を添える** — 「203,499件」が CSV行数なのか DB行数なのかで
   意味が変わる。行数・件数・ユニーク数を区別する
2. **測定条件を書く** — 初回か定常か、どの計測手段か。書かないと後から検証できない
3. **観測から原因を逆算した結論は疑う** — 「47秒 ÷ 24クエリ = 1クエリ2秒」は
   もっともらしいが誤り。原因を直接測れば0.066秒だった
4. **帳尻を確認する** — 「補完前 + 採用 = 現在」が合わないことで定義の誤りに気づけた
5. **測定器のオーバーヘッドを疑う** — 全項目が同じ値に揃ったら、測っているのは
   対象ではなく計測手段
